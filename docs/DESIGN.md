# SDLC Multi-Agent Automation Suite: Design Document (Prototype v1)

## 1. Goal

Simulate a credit-risk engineering SDLC (ticket → design → code → review) with three coordinated agents on LangGraph, passing structured Pydantic state. The prototype is instrumented with metrics and evaluated against hand-crafted tickets with known-good outcomes. Success means correct detection and flagging, not forced task completion.

**Non-goals for v1:** Supabase, RAG, production-grade error handling, multi-repo support, real Git hosting integration.

## 2. Architecture Overview

```
Ticket → [Agent 1: Design] → route → [Agent 2: Dev] → route → [Agent 3: Review] → route → END
              ↑                            ↑                           |
              |                            └──── one retry ────────────┘
              └──── human answers (HITL) ──┘
```

Grounding is structured lookups only: the toy repo's file state, a repo manifest, and a YAML config of org standards. No retrieval over documents.

## 3. Shared State (Pydantic)

A single `PipelineState` object flows through the graph:

- `ticket`: title, description, acceptance_criteria
- `design`: DesignDoc or None
- `dev_result`: DevResult or None
- `review`: ReviewResult or None
- `human_qa`: list of {question, answer, asked_by_agent}
- `retry_count`: int (max 1 for dev after review rejection)
- `pipeline_outcome`: one of `approved`, `rejected`, `blocked`, `needs_human_unresolved`, `error`
- `run_metadata`: run_id, model, timestamps

No free-text handoffs. Every inter-agent payload is a validated model. Human answers are the only free text.

## 4. Agents

### Agent 1: Design Agent
**Input:** ticket, repo manifest, human_qa history
**Tools:** read-only `list_files`, `read_file`, `search_code`
**Output (DesignDoc):**
- summary
- affected_modules (validated programmatically against the real file list; invalid names trigger a schema retry)
- approach
- edge_cases
- test_scenarios
- open_questions: list of blocking questions for the human
- ambiguity_flags: list of {type: `vague` | `contradictory` | `missing_dependency`, detail}
- confidence: 0 to 1

**Behavior:** If acceptance criteria are vague, contradictory, or depend on unknown information (e.g., "which DTI threshold?"), it must populate `open_questions` and flags instead of guessing scope. Once answered, the design is regenerated with the answers in context.

### Agent 2: Development Agent
**Input:** approved DesignDoc, human_qa history, optional review feedback
**Tools:** `read_file`, `write_file`, `list_files`, `search_code`, all scoped to a per-run temp copy of the repo
**Output:** either
- Success: {files_changed, tests_added}, with the **diff generated by code** (`difflib`) after writes, not by the model
- Blocked: {blocked: true, reason, open_questions}

**Behavior:** Not forced to produce a diff. If it hits unaccounted-for complexity (e.g., a conflicting existing function with callers), it returns blocked with a reason and a question for the human where a human answer could unblock it.
**Guardrails:** tool loop capped at 8 iterations (hitting the cap is logged and treated as `blocked` with reason `iteration_cap`); `write_file` rejects paths outside the repo.

### Agent 3: Review Agent
**Input:** code-generated diff, original DesignDoc, YAML config
**Tools:** `run_tests()` returns pytest results plus pytest-cov per-file JSON
**Deterministic checks (code, not LLM):**
- Coverage per file vs. YAML thresholds
- Naming conventions via AST
- Test pass/fail
- Test tampering (deleted tests or assertions)

**LLM role:** interpret the deterministic results plus the diff against the design, and decide `risk_level` and `approval_decision`. Hard gates in code stop the LLM from approving over failing tests or coverage gaps.
**Output:** {risk_level, violations, missing_coverage, approval_decision, open_questions}

## 5. Human-in-the-Loop (HITL)

Any agent can pause the pipeline by returning non-empty `open_questions`. This covers scoping questions, missing dependencies, or unclear requirements.

**Mechanism:** LangGraph `interrupt` with a checkpointer. The graph pauses, the questions are shown to the human (CLI prompt for v1, optional Streamlit form later), the answers are appended to `human_qa`, and execution resumes at the agent that asked.

**Rules:**
- Question cap: max 2 HITL rounds per agent per run. If still unresolved, the outcome is `needs_human_unresolved`. This prevents infinite question loops.
- Question quality: each question needs a `why_blocking` field. Non-blocking uncertainties go into `assumptions` or `edge_cases`, not questions, so the agent doesn't over-ask.
- **Eval mode:** a `SimulatedHuman` returns scripted answers from the ground-truth file (or "I don't know." for a test that expects unresolved). This keeps evaluation automatic and repeatable. Interactive mode is used for demos.
- Every HITL event is logged (agent, question count, round), and it counts as `flagged`, not `fail`.

## 6. Routing Logic (LangGraph Conditional Edges)

| After | Condition | Next |
|---|---|---|
| Agent 1 | open_questions non-empty | HITL → back to Agent 1 |
| Agent 1 | clean design | Agent 2 |
| Agent 2 | blocked with answerable question | HITL → back to Agent 2 |
| Agent 2 | blocked, not answerable / iteration cap | END (`blocked`) |
| Agent 2 | success | Agent 3 |
| Agent 3 | approve | END (`approved`) |
| Agent 3 | reject, retry_count < 1 | Agent 2 with review feedback in state |
| Agent 3 | reject, retry exhausted | END (`rejected`) |
| Any | HITL rounds exceeded | END (`needs_human_unresolved`) |
| Any | schema validation fails after retries | END (`error`) |

Pipeline-level outcomes are tracked separately from per-agent outcomes.

## 7. Toy Repo: Loan Eligibility Calculator (5–8 files)

```
loan_repo/
  loan_calc/
    models.py
    dti.py                 # calculate_dti(), 3 callers, planted conflict
    income_verification.py
    rates.py               # interest rate tiers
    risk_scoring.py        # SENSITIVE, coverage threshold 90%
    eligibility.py         # SENSITIVE, coverage threshold 85%
  tests/
    test_*.py
config/
  standards.yaml           # naming rules, per-module coverage thresholds
```

**Planted traps:**
- `dti.py::calculate_dti()` exists with different semantics (back-end vs. front-end DTI) and is used by 3 callers, which triggers the blocked path.
- `risk_scoring.py` is marked sensitive with a 90% threshold.
- Baseline suite is fully passing at roughly 85% overall coverage, so any gap is attributable to new changes.
- **Isolation:** every run copies the repo to a fresh temp directory. Runs never contaminate each other.

## 8. Evaluation

### Ground truth file (written before any agent code)
`data/ground_truth.yaml` lists, per ticket: expected Agent 1 outcome, expected Agent 2 outcome, expected Agent 3 outcome, expected pipeline outcome, scripted HITL answers.

### 8 tickets

| # | Type | Tests | Expected |
|---|---|---|---|
| T1 | Clean, simple (add rate tier) | Negative control | Approve, no flags |
| T2 | Clean, moderate (new eligibility rule) | Negative control | Approve, no flags |
| T3 | Missing coverage on sensitive module | Agent 3 | Flags missing_coverage, rejects |
| T4 | Missing coverage on non-sensitive module | Agent 3 | Flags per threshold |
| T5 | Vague criteria ("make eligibility stricter") | Agent 1 | Ambiguity flag (vague) + HITL question |
| T6 | Contradictory criteria (DTI > 40% vs. up to 45%) | Agent 1 | Ambiguity flag (contradictory) |
| T7 | Conflicting existing `calculate_dti()` | Agent 2 | Blocked with reason, no fabricated diff |
| T8 | Naming violation | Agent 3 | Flags violation |

Coverage-gap tickets depend on how the dev agent behaves, so T3/T4 use a **fixture-diff test** for Agent 3 in isolation, plus the end-to-end run where the ticket itself forbids touching `tests/`.

### Two evaluation modes
1. **Per-agent (isolated):** Agent 1 on tickets, Agent 2 on hand-written design docs, Agent 3 on fixture diffs (good and bad). Gives a clean accuracy signal.
2. **End-to-end:** all 8 tickets through the full graph with SimulatedHuman. Gives realistic, noisier pipeline accuracy.

### Variance handling
Temperature 0; each ticket run 3 times (final batch). Report pass rate per ticket and per agent.

### Correctness definitions
- **Agent 1:** correct if ambiguity flag presence/type matches ground truth; clean tickets must have no blocking questions (false positive check).
- **Agent 2:** correct if blocked matches expected; on non-blocked tickets, diff is applied and existing tests still run.
- **Agent 3:** correct if approval_decision and planted violations match ground truth.
- **Uncertainty-surfacing rate:** among tickets where uncertainty was planted, how often the responsible agent surfaced it instead of proceeding.
- **False positive rate:** among clean tickets, how often an agent raised unnecessary flags, questions, blocks, or rejects.
- **Confidence calibration:** does Agent 1's confidence correlate with correctness?

## 9. Edge Cases Covered

- Agent asks a vague or unanswerable question → schema requires `why_blocking`; round cap forces termination.
- Human answer is empty or "don't know" → counts toward round cap, then `needs_human_unresolved`.
- Human answer contradicts earlier answers → design regenerated; a new ambiguity flag can be raised.
- Agent 1 hallucinates module names → programmatic validation against the file list.
- Agent 2 writes outside the repo or edits tests to force a pass → path scoping; tampering check flags modified/deleted tests.
- Agent 2 loops on tools → 8-iteration cap.
- Structured output fails validation → up to 2 schema retries, logged as a metric, then `error`.
- Generated code breaks existing tests → caught by real `run_tests()`.
- Empty or malformed ticket → input validation before Agent 1.
- Review reject loop → single retry cap.
- Repo contamination between runs → fresh temp copy per run.
- LLM API timeout or rate limit → retry with backoff, then `error`.
- pytest hangs → 60s subprocess timeout, treated as failed tests.

## 10. Metrics and Storage (SQLite)

- **`runs`:** run_id, batch_id, ticket_id, mode, repeat_index, model, prompt_version, timestamps, pipeline_outcome, pipeline_correct
- **`agent_runs`:** run_id, agent, attempt, latency_ms, tokens_in, tokens_out, cost_estimate, outcome (pass/fail/blocked/flagged), correct, schema_retries, tool_calls, hitl_rounds, hit_iteration_cap, uncertainty_planted, uncertainty_surfaced, confidence
- **`hitl_events`:** run_id, agent, round, n_questions, answer_blank
- **`pricing`:** model, input_per_1k, output_per_1k (config-driven cost estimates)

A tracking decorator wraps every agent node, and logging is added right after the schemas so no run data is lost.

## 11. Dashboard (Streamlit, 3 core panels)

1. **Latency by agent** (box plot)
2. **Cost per ticket** (stacked by agent)
3. **Accuracy:** per-agent correctness, uncertainty-surfacing rate, false positive rate, plus a per-ticket pass-rate table across repeats

Stretch: confidence calibration plot, HITL rounds per ticket, pipeline outcome funnel.

## 12. Stack

Python 3.11+, LangGraph (with checkpointer for interrupts), LangChain `init_chat_model`, Pydantic v2, pytest + pytest-cov, SQLite, Streamlit, pandas, plotly, typer, rich, tenacity, YAML config.

## 13. Success Criteria

- Pipeline runs end-to-end on all 8 tickets with no crashes, and every run ends in a defined pipeline outcome.
- Agent 3 flags planted coverage gaps in ≥2/3 cases (measured on fixture diffs and e2e).
- Agent 1 correctly flags ambiguous tickets and does not raise blocking questions on clean tickets.
- Agent 2 reports blocked on the planted-conflict ticket and never fabricates a diff.
- HITL pauses correctly on any open question, resumes with the answer in state, and terminates cleanly when unresolved.
- False positive rate on clean tickets is reported alongside detection rates.
- Dashboard shows all results without manual log-digging.
